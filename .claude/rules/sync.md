# Sync with the mobile app (shared folder)

The design lives in the mobile repo (`simple-budget-mobile`): ADR-0008 (the model: per-row last-writer-wins by `uuid`, tombstones kept forever) and ADR-0009 (one file per device, `simple-budget-sync-<deviceId>.json`, in a folder a sync client shares). Read them before changing anything here; this repo implements the same protocol and must behave exactly like the mobile app.

- **`electron/main/sync/` is pure**: stamps, the merge, the planner (which files to merge, offer or leave) and the file codec. No database, no files, no clock (callers pass `now`). The database store is `db/syncStore.ts`; the folder, the engine and the schedule are in `electron/main/syncing/` (below).
- **The contract with the mobile app is the three golden files in `test/golden/sync/`** (`sync-merge.json`, `sync-plan.json`, `sync-file.json`). They are written by hand in the mobile repo and copied here by `scripts/sync-golden-from-mobile.sh`, which records the mobile commit in `test/golden/sync/SOURCE`. This is the opposite direction from `test/golden/projection.json`: **never edit them here**, and never copy them by hand. A case that looks wrong is fixed in the mobile repo, in both apps together, and the script re-run.
- **Stamps** are text in the form Java's `Instant.toString()` writes (`2026-11-05T10:00:00Z`, a fraction only when there is one). Compare them as instants (`compareStamps`), never as text.
- **Numbers in a file are safe integers** (cents below 2^53). A file with a bigger one is skipped, not rounded.
- **A file is merged whole or not at all.** Anything wrong with it skips the whole file for this round (see `SkipReason`).
- **Files here run through Node's type stripping or vitest only**: no enums or parameter properties (`erasableSyntaxOnly`).
- **Every row has a `uuid` and an `updated_at`, and deletions are recorded** (migration 007): `deleted_rows(table_name, uuid, deleted_at)` holds a tombstone for every row ever deleted, kept for good and never pruned, with the same names as the mobile app's table. The write rules are in `backend.md`; `updated_at` and `deleted_at` are stamps (`2026-11-05T10:00:00Z`), and a deleted account leaves a tombstone for each item and correction it takes with it, all at one stamp.
- **`db/syncStore.ts` is the database side of sync**: it reads this computer's state as a `DeviceState` and applies a merged state back, reading, merging and writing in one transaction (`mergeInto`), or replaces everything with a given state (`replaceWith`, the loser of a first link). It keeps the stamps rows were merged with (a merge never restamps), writes exactly the merged tombstones, and removes rows the merge dropped without tombstones of its own. Children go before accounts on removal and accounts before children on insert, because the database enforces its keys. `db/syncMapping.ts` is the one place that maps between columns and the file's field names.
- **Merging the same files again can still change something once**: a row the merge dropped as an orphan leaves no tombstone, so a tombstone another device still holds for it comes back on the next round (true history). It settles after that, and the engine must not treat "changed" as "keep publishing" forever.
- **`electron/main/syncing/` runs it**: `folder.ts` (the folder on disk), `settings.ts` (this machine's sync settings), `engine.ts` (one sync, and settling a first link), `coordinator.ts` (the schedule and what the screen shows), `changes.ts` (the API tells it the budget changed), `index.ts` (the real wiring; `getSyncCoordinator()`, made on first use so importing it starts nothing). The engine and coordinator take their dependencies as arguments so tests can use an in-memory folder and a fake engine.
- **The folder is the backup folder** (`backup/settings.ts`): one place to set up, already one a cloud client keeps in step. Sync is on only when `sync-settings.json` says so *and* a backup folder is set. `DirectorySyncFolder` reads and writes only files named like a sync file (`simple-budget-sync-<id>.json`) and never the snapshots or anything else that shares the folder, and it writes a file as a whole (a temporary `.simple-budget-sync-….tmp` beside it, then a rename) so a cloud client never uploads half of one.
- **`sync-settings.json` lives beside the database, not in it** (like `backup-settings.json`): the device id, whether sync is on, the first links decided and the last read and write describe this machine, so a restored snapshot must not carry them to another computer. The device id is made the first time it is needed and never changes.
- **The schedule**: at start, every minute (not while one is still running), about 3 seconds after the last change made through the app, on request, and once more on the way out if something changed since the last sync (bounded by the quit timeout). The API router calls `notifyBudgetChanged()` after every successful write except setting the backup folder and taking a snapshot. A sync that is off does no file or database work.
- **The screen is the Sync section of the Backups dialog** (`src/components/menus/account/Backups/SyncSection.tsx`, with `FirstLinkDialog.tsx`), over `GET /api/sync` and `POST /api/sync/{enable,disable,now,resolve}` (`electron/main/routes/sync.ts`), and the hook `src/data/useSync.ts` (which looks again every 5 seconds while sync is on). It says only what this computer did. The route settles a first link from the offer the coordinator last found (`offerFor`), never from what the request says, and refuses with 409 when the device has written since the person looked. Taking the other device's data reloads the app, as a restore does. Device names are shown with i18next's escaping off (React already escapes), or "Sebastien's Pixel" would read `Sebastien&#39;s Pixel`.
- **Confirmations that destroy data say so when sync is on**: the wipe asks the server (`fetchSyncEnabled`) and uses `WipeConfirmSync`, because with sync on the other devices follow.
